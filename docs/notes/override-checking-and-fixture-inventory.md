# Override conformance checking, and the test fixture inventory

This chapter covers the `agent/override` slice — SLS 5.1.4 "Overriding" and
SLS 5.2.6 ("needs to be abstract"), neither of which scala-rs implemented at all,
so that a wrong override or an unimplemented abstract member typechecked cleanly
and then blew up at run time.

Because that slice was the one that had to prove it introduced no false
diagnostics, it also carries the project-wide inventory of test fixtures: which
fixture exercises what, which mode it runs in (private runtime,
`--scala-library`, or a dual run against real scalac 2.13.16), and what stdout it
is pinned to. That inventory makes up the bulk of what follows.

### Override conformance checking (`agent/override`)

SLS 5.1.4 "Overriding" (nsc's `RefChecks.checkOverride`) and SLS 5.2.6
("needs to be abstract") were **missing entirely**, and the following two were silently accepted.

```scala
trait It[A] { def next(): A }
val i = new It[Int] { def next(): String = "x" }
println(i.next())          // passes type checking, then ClassCastException on the caller's unbox

abstract class B { def f: Int }
class D extends B          // passes type checking, then AbstractMethodError the moment it is called
```

The rules themselves live in `crates/typer/src/override_check.rs` as **pure functions over the symbol
table** (the same shape as `traitparent.rs`), and `check.rs` only gains two lines of calls at the end
of `type_class` / `type_module`. Every diagnostic wording was **collected by running the real scalac
2.13.16 over the same source** (not from `javap`). The overridden side is echoed
**in the form seen from the override site** (`def next(): A` of `trait It[A]` becomes
`def next(): Int` under `new It[Int]`).

| Rule | scalac's wording | Before | After |
| --- | --- | --- | --- |
| 1. Result type is covariant | `incompatible type in overriding` | missing | present |
| 2. Parameter types are invariant (differing ones make it an overload) | `method f overrides nothing.` + `Note: …` | missing | present |
| 3. Whether the `override` modifier is required | `` `override` modifier required to override concrete member: `` / `method h overrides nothing` | missing | present |
| 4. A deferred re-declaration cancels out the concrete implementation below it | `class C needs to be abstract.` + `No implementation found in a subclass for deferred declaration` | missing | present |
| 5. `final` cannot be overridden | `cannot override final member:` | missing | present (source-derived only; see the remaining item below) |
| 6. Visibility may only be widened | `weaker access privileges in overriding` | missing | present |
| 7. A `val` may cover a `def` but not the reverse, and a concrete `var` cannot be covered | `stable, immutable value required to override:` / `mutable variable cannot be overridden:` | missing | present |
| 8. Type parameter count and bounds | `overrides nothing.` / `incompatible type in overriding` | missing | present |
| 9. Unimplemented abstract members | `class X needs to be abstract.` / `object creation impossible.` | missing | present (source / Java classfile derived only; see the remaining item below) |

**Since this slice fixes over-acceptance, false diagnostics are the biggest risk.** Across slick's 184 files we get
**346 errors / 64 files** (before starting) → **346 / 64** (after implementing), i.e. **the multiset of diagnostics
does not change by a single entry**. There were 5 causes behind the false diagnostics I killed off from an intermediate
version that had climbed to 502, and none of them was a "rule" — every one was **an approximation in the symbol table**.

1. **The flags on prelude members cannot be trusted.** `prelude::method` sets **`Flags::FINAL` on every
   member**, so `override def toString` came out as "overriding a final", and conversely there is no way
   to express "deferred", so the genuinely abstract `Product.productArity` looked concrete and every
   hand-written `Product` was being asked for an `override`. Members coming from the pickle
   are built with `Flags::EMPTY`, so they have the same problem. I gated on `modifiers_are_known`
   (after `prelude_end` and with an empty `pickled_origin`).
2. **Do not compare types you cannot trust.** `ClassTag[C[Any]]` vs `ClassTag[_]`,
   `Builder[E, C[E]]`, `BasicBackend.Session` — comparisons involving type parameters, abstract type members,
   unreduced applications, or wildcards are scala-rs approximations, so for types that are not `robust` we
   stay quiet and treat them as "matching" (that accounted for 150 false diagnostics).
3. **Do not check members that do not write a result type.** nsc's namer types a member with no result type
   **using the overridden member's result type as the expected type**, so it is impossible in principle for the
   inferred result type not to conform. Our inference is an approximation, and slick's
   `override def toString = { … }` comes out as `Any`.
4. **A plain constructor parameter is not a member** (nsc's
   `OverridingPairs.Cursor.exclude`). slick's
   `class JdbcFunction(name: String) extends FunctionSymbol(name)` is `private[this]`,
   so it covers nothing. A written-out `private[this] val` we do diagnose, just like scalac.
5. **Lambda parameters in field initializers were landing in the class's member list.**
   The `fs` in `protected lazy val pkNames = pkSyms.map { fs => … }` gets the class as its owner,
   so it collided with the base class's `fs` and demanded an `override`.
   Only a `PARAM` that lives in `ctor_fields` counts as a member.

The fixtures use the prefix `ov`, and to avoid conflicts they live in `crates/cli/tests/override.rs`.
The accepting case `ov_ok.scala` gathers **every legal shape of override** (a covariant result type,
overloading, implementing a deferred member, a `final` sibling, widening visibility, overriding a `def`
with a `val`, implementing an abstract `val` with a `val` constructor parameter, shadowing by a plain parameter,
relaxing a bound, making a member concrete in an anonymous class, `def f` and `def f()` matching each other, overriding
`toString`) into one file, and runs it under `java -Xverify:all` in **both the private runtime and `--scala-library`**.
`expected/ov_ok.txt` is **the real scalac 2.13.16 output verbatim**. The 14 rejecting fixtures knock out rules
1 through 9 one at a time, and `rejected_once` pins down both that they are **rejected in both modes** and that
**there is exactly one error, the same as the real scalac** (a cascade, or a diagnostic that appears in only one of the
modes, is just as much a failure as a missing check).

Along the way I fixed one more leftover from `agent/anonbridge`: **no `pop` was emitted when discarding the result of
a member that erasure had turned into one returning `Object`**. The `get` of `trait Box[A] { def get: A }`
is **a `def` with no parameter list**, so the call is a bare `Select` with no `Apply`,
and it never hit the `Apply` arm of `unit_stat_leaves_ref`. In straight-line code the
verifier stays quiet so nobody notices, and the moment a branch that requires a stackmap frame (`try` / `while`)
comes along you get `VerifyError: Inconsistent stackmap frames`. `ov_unitpop.scala` runs all four shapes —
the `Apply` shape, the bare `Select` shape, calling while still a type parameter, and the back edge of a `while` —
in both modes, and `ov_nilary_unit_select_is_popped` uses `javap -c` to check that the `pop`
really is emitted.

I added the `override` modifier to two existing fixtures (`java_override.scala` / `implicit_specific.scala`).
Both are sources that **the real scalac 2.13.16 rejects as they stand**
(for `java_override`, because Java's `@Override` **annotation** is not a substitute for Scala's `override`
**modifier**; for `implicit_specific`, because `pick()` stops at the typer and never reaches
RefChecks, which is the only reason scalac got away with saying nothing), and they were only
passing because the check did not exist. The intent of the tests (accepting `@Override` / implicit specificity) is
unchanged.

The fixtures for the `agent/patbind` slice (the bound type of `x @ Pat`, `null` patterns, `==` against null) use the prefix `pb`
(`pb_bind` / `pb_null` / `pb_lit` / `pb_eqnull` / `pb_nullseq` / `pb_null_bad`), and to avoid conflicts they live in
`crates/cli/tests/patbind.rs`. Every one of these was a bug that **passed type checking and then blew up at runtime**, so
the tests run all three ways (private runtime / `--scala-library` / real scalac 2.13.16) and check that
the stdout matches everywhere. `expected/pb_*.txt` is the real scalac output verbatim.
`pb_bind.scala` gathers nested `@`, combination with a type pattern (`case n @ (_: N)`), guards, extractors,
tuples, inside a `catch`, and narrowing from `Any` to a primitive, all into one file.
`pb_null.scala` puts `null` through 8 kinds of pattern: literal / stable identifier / type pattern / `AnyRef` / extractor / case class /
tuple / `case _`. `pb_lit.scala` covers `Long` / `Float` / `Double` /
`Char` scrutinees plus a boxed constant against a reference scrutinee. `pb_eqnull.scala` covers
the `==` / `!=` side: the reference tests `x == null` / `null == x`, and a
null receiver under the private runtime (`(null: String) == "a"` used to NPE). `pb_nullseq.scala` covers
`Seq` / `::` / `Array[Int]` / `()`, and since it needs `SeqFactory$UnapplySeqWrapper$` it is
library-dual-run only. `pb_null_bad.scala` pins down that `(x: Int) match { case null => … }` gives
`type mismatch; found: Null(null)`, the same as nsc.

The fixtures for the `agent/conspat` slice (extractors nested inside a `::`, the call site of `unapply`,
`MatchError` from an exhausted `match`) use the prefix `cp`
(`cp_cons` / `cp_infix` / `cp_seq` / `cp_err` / `cp_cons_bad`), and to avoid conflicts they live in
`crates/cli/tests/conspat.rs`. These too were bugs that **passed type checking and then blew up at runtime**,
so the tests run all three ways (private runtime / `--scala-library` / real scalac 2.13.16) and check that
the stdout matches everywhere. `expected/cp_*.txt` is the real scalac output verbatim.
`cp_cons.scala` gathers `case P(v) :: t`, depth 2 (`case P(a) :: P(b) :: _`), an extractor on the right of `::`
(`case _ :: P(v) :: _`), tuples (`case (a, b) :: _`), guards, `@` bindings
(`case (p @ P(v)) :: _`), type patterns (`case (p: P) :: _`), `case Some(P(v))`,
a constant pattern against `Option[Any]`, the stable identifiers in `case P(v) :: Nil` / `case Some(Nil)`,
and the `case h :: t` that already worked before, all into one file. `cp_infix.scala` covers
a user-defined infix extractor (`object ~`) and the shape where the extractor's argument type is narrower than the scrutinee
(`case Some(Two(a, b))` against `Option[Any]`). Those two also run **in the private runtime**.
`cp_seq.scala` covers `case List(P(a), Q)` / `case Seq(P(a), _*)` and an `unapply` returning
`Tuple3`, and since the `Seq` / `List` extractor patterns and `Tuple3` only exist in the jar it is library-
dual-run only. `cp_err.scala` checks in both modes that an exhausted `match` becomes a `scala.MatchError`
(both the class name and the message). `cp_cons_bad.scala` pins down that
`case P(a, b)` (wrong arity) and `case Nope(a) :: _` (nonexistent extractor) are diagnosed.

The fixtures for the runtime representation of trait `val` / `override val` / `var` and the synthetic members of a `case object` use the prefix `tval` (`tval` / `tval_bad`), and for the same reason they live in `crates/cli/tests/traitval.rs`. `tval.scala` runs in both the private runtime (`--no-scala-library`) and library dual-run, and `expected/tval.txt` is **the real scalac 2.13.16 output verbatim** (all three modes were confirmed byte-for-byte identical). The bytecode-side invariants are pinned down by two more tests. `trait_val_setters_follow_nsc_names` uses `javap -p -c` to check that the mixin setter has the same name as nsc's, `Named$_setter_$label_$eq`; that in a class that did `override val` that setter has an empty body (no `putfield`); and that an assignment to a trait's `var` is a `count_$eq` call rather than a `putfield`. `case_object_members_are_on_the_module_class` checks that `toString` / `productPrefix` / `hashCode` / `productArity` are emitted on `Asc$`. `tval_bad.scala` pins down that assigning to a trait's `val` gives `reassignment to val`.

The fixtures for value classes + universal traits, a unary minus on the line after a `}`, and name resolution of `X.type` use the
prefix `vcls` (`vcls` / `vcls_nl` / `vcls_arr` / `vcls_hnil` / `vcls_bad`), and for the same reason they live in
`crates/cli/tests/valclass.rs`. `vcls.scala` (value class + universal trait, assignment
to `Any`, pattern matching, `==`, `asInstanceOf`, a `-1` on the line after a `}`) and `vcls_nl.scala`
(newline rules only: a `-` right after a `}` / `if` / `)` / an identifier, continuation of a line-ending operator, inside parentheses,
and `if` / `match` in statement position) both run in **the private runtime and library dual-run**.
`vcls_arr.scala` (`Array[Meters]` / `List[Meters]` / `Option[Meters]` / generic methods /
case class fields / `Set`) and `vcls_hnil.scala` (`HNil.type` where `import syntax._` has hidden the type name,
the package-qualified `p.HNil.type`, and the nested `object`'s
`ColumnOption.AutoInc.type`) need `List.apply` / `Array.apply`, so they are library-dual-run only.
Every `expected/*.txt` is the real scalac 2.13.16 stdout verbatim.
`vcls_bad.scala` pins down that three things are not silently accepted: touching the underlying value through a universal trait (`u.n`), a nonexistent member,
and using a `def` for an `X.type`. On the bytecode side we check with
`vcls_classfile_matches_nsc_shape` (`Meters implements Univ`, the statics `describe$extension(int)` /
`plus$extension(int, int)` / `equals$extension` / `hashCode$extension`, and `equals` /
`hashCode`) and `vcls_boxes_into_the_value_class_not_its_underlying_box` (that what precedes a call taking a
universal trait is `new Meters` and not `Integer.valueOf`).

The fixtures for **type aliases** in a jar's package object use the prefix `pkgalias` (`pkgalias` / `pkgalias_bad`), and for the same reason they live in `crates/cli/tests/pkgalias.rs`. `pkgalias.scala` uses only aliases that exist nowhere but the `scala` package object's pickle (`NoSuchElementException` / `Throwable` / `UnsupportedOperationException` / `IllegalArgumentException` / `Exception` / `IterableOnce[A]` / `Seq[A]`), and is library-dual-run only (`pkgalias_without_library_is_diagnosed` also checks that under `--no-scala-library` it is diagnosed as `not found: value NoSuchElementException`). `pkgalias_bad.scala` pins down that a name the package object does not declare is not silently accepted. `expected/pkgalias.txt` is the real scalac 2.13.16 output.
