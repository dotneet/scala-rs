# gitbucket

Where this compiler stands on [gitbucket](https://github.com/gitbucket/gitbucket),
the third real-world benchmark after slick and cats, and the first that is an
*application* rather than a library.

Two things make gitbucket different from the first two benchmarks:

* **It uses slick.** Not the slick we compile from source — the published
  `slick_2.13-3.4.1.jar`, through `blocking-slick` — so it measures whether
  reading slick's pickles is good enough for a program that actually calls it,
  including slick's `TableQuery` and `mapTo` macros.
* **140 of its 354 sources are generated**, by the Twirl template compiler
  (`sbt-twirl` turns `src/main/twirl/**/*.scala.html` into Scala). Those files
  are machine-written and unlike anything a person types.

### What sbt actually compiles

Read off `build.sbt` and `sbt "export Compile/dependencyClasspath"`, not
guessed:

* **`-Xsource:3-cross`** for the 2.13 build. Load-bearing: gitbucket
  cross-builds for Scala 3 and its sources use 3's spellings — intersection
  self types written `A & B`, `import x.*`, `case p <- gen` in
  for-comprehensions.
* The rest of `scalacOptions` is `-deprecation -language:postfixOps
  -opt:l:method -feature -Werror -Wunused:imports -Wconf:…`. Only
  `-language:postfixOps` matters here; the others are warning policy and the
  optimiser.
* **No compiler plugins.** Every diagnostic is ours.
* Notable dependencies: `slick 3.4.1` (through `blocking-slick 0.0.14`),
  `scalatra 3.2.1`, `json4s 4.1.1`, `jgit 6.10.1`, `twirl-api 2.0.9`,
  `scala-xml 2.4.0`, `h2 2.4.240`.

## Measuring and running it

```
GITBUCKET_LOG=<your own path> GITBUCKET_RUN=<your own path> tests/gitbucket_measure.sh
```

It rebuilds *this* checkout's `target/release/scala-rs` (or uses
`SCALA_RS=<binary>`), re-fetches the material at the pinned revision when it
is missing, has sbt write the Twirl sources and export the dependency
classpath, compiles the 3 Java sources with javac onto the classpath, and
writes every path per invocation. `GITBUCKET_LOG` and `GITBUCKET_RUN` default
to per-invocation paths under `SCALA_RS_FIXTURE_ROOT`; set them when you want
to keep the output. It prints one line:
`files= skipped= errors= files_with_errors= classes= compiler_exit= java_sources=`.

* `GITBUCKET_MODULES=scala` measures the hand-written sources alone;
  `GITBUCKET_MODULES=twirl` the generated ones alone (which do not typecheck
  without the hand-written ones); the default is both.
* `GITBUCKET_EXCLUDE` holds files out by basename, and `GITBUCKET_JAVA=0`
  leaves the Java sources out. Both default to the full input set and exist
  only for comparisons with historical measurements.

A compile measure says nothing about whether the output works.
`tests/gitbucket_run.sh [prog-name ...]` is the differential execution test:
it compiles gitbucket with scala-rs and with real scalac, compiles the client
programs in `tests/gbrun/` with real scalac against **both** builds, and runs
them under `java -Xverify:all` against an in-memory H2 database, comparing
stdout byte for byte. The clients drive gitbucket's own tables: DDL, rows
round-tripped through `mapTo`, a join, `sortBy`, `groupBy`, the Date/Timestamp
`MappedColumnType`, and a self-typed `import profile.api._` component. A
difference when a client compiled against scalac's gitbucket runs on our
classes is a **codegen** defect; a failure compiling against our gitbucket is
a **pickle** defect. See its header for the environment variables. The merge
gate runs both scripts.

## Where we stand

Per `tests/BASELINE.md` (gate `ff08907d`, 2026-09-14),
`tests/gitbucket_measure.sh` compiles all **354 inputs with 0 errors and emits
1317 class files**, and `tests/gitbucket_run.sh` runs **6/6** client programs
with `known_fail=0`. The merge gate requires zero errors, `java_sources=3`, and
no run failure outside the (empty) known-failure ledger.

## Known gaps

* **gitbucket's own test sources do not compile yet.** The last recorded
  measurement (2026-09-14, not merge-gated) found 9 errors in 5 of the 32 test sources:
  five Slick query result projections (`Query[E, Any, Seq]`), one missing
  `Context` implicit, one `DatabaseFactory.forURL` prefix error, and two
  ScalaTest emptiness ambiguities in which implicit specificity reduces every
  candidate type parameter to a wildcard.
* Recorded as still open when the run harnesses landed:
  `Database.forURL` resolving to `BasicBackend`'s factory through
  `import blockingApi._`, and polymorphic aliases being dealiased before
  pickling.
