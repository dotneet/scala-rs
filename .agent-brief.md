# scala-rs 共通ブリーフ（サブエージェント用）

## プロジェクト
Rust で書いた Scala 2.13 サブセットのコンパイラ。JVM classfile を出す。
- ワークスペース: crates/{span,lexer,parser,typer,backend,driver,cli}
- 型検査・シンボル表: crates/typer/src/{check.rs,prelude.rs,symbol.rs,classpath.rs}
- コード生成: crates/backend/src/{gen.rs,runtime.rs,pickle.rs}
- E2E: crates/cli/tests/e2e.rs ＋ tests/fixtures/*.scala ＋ tests/fixtures/expected/*.txt

## 作業開始時の必須手順
1. **必ずローカルの `main` から分岐する**: `git switch -c <branch> main`（この 1 コマンド）。
   - `git switch main` は**使わないこと**。`main` は親のワークツリーでチェックアウト
     済みなので、あなたのワークツリーでは失敗します。失敗に気づかず `origin/main`
     から切ると、**63 コミット古いツリー**で作業することになります（実際に起きました）。
   - 始める前に `git log --oneline -1 main` と `git log --oneline -1 origin/main` の
     **両方**を出し、`main` の方が新しいことを確認すること。`origin/main` は古い。
   - slick の基準値がブリーフに書かれた数字と食い違ったら、**それは分岐元が違う証拠**
     です。作業を始める前に報告してください。
2. slick の計測は **`tests/slick_measure.sh` をそのまま使う**（コピーしない）。
   スクリプトは**自分のワークツリーの** `target/release/scala-rs` をビルドして測ります。
   数字が「修正しても 1 も動かない」ときは、まず自分のバイナリを測れているか疑って
   ください（以前は親リポジトリのバイナリを測る作りで、実際に 2 回踏まれています）。
   書き込み先はすべて呼び出しごとに分かれるので、他のエージェントと同時に走らせても
   干渉しません。ログの場所を変えたいときだけ `SLICK_LOG=<path> tests/slick_measure.sh`。
   **コピーして使うと、共有していた `generated/` と `measure.txt` を踏み合って
   互いの数字を報告することになります**（実際に 711 と 745 の食い違いが起きました）。
   基準値がブリーフと食い違ったら、まずこれを疑って報告してください。
3. 変更前後の数字を必ず両方報告する。

## 絶対ルール
1. **スタブ禁止**。未実装は必ず診断（error）を出す。「動いたことにする」実装は不可。
2. `cargo test --workspace` を**必ずグリーン**に保つ。既存テストを消さない・弱めない。
3. `cargo fmt --all` と `cargo clippy` の新規警告ゼロ。
4. 実 scala-library に対する **dual-run** で検証する。jar: `/tmp/scala-rs-lib/scala-library-2.13.16.jar`
5. 実装した機能は必ず fixture（正常系 `<name>.scala` + `tests/fixtures/expected/<name>.txt`、
   異常系 `<name>_bad.scala`）と e2e テストを追加する。
6. README.md の該当節（「実装している言語サブセット」「テスト」「Remaining」）を日本語で更新する。

## 2モードあることに注意
- `--scala-library <jar>`: 本物の scala-library 2.13.16 ABI にリンク（`library_abi = true`）。
- `--no-scala-library`: 自前の私有ランタイム classfile（crates/backend/src/runtime.rs が生成）。
新メンバを足すとき、私有ランタイム側で裏付けられないものは `library_abi` でゲートし、
非 jar モードでは**きちんと診断**を出すこと（黙って通さない）。

## マージ衝突を避ける
- prelude への追加は**新しいモジュールファイル** `crates/typer/src/prelude_<topic>.rs` に書き、
  `prelude.rs` からは 1 行だけ呼ぶ（`mod` 宣言は crates/typer/src/lib.rs に 1 行）。
- e2e テストは **ファイル末尾に追記**する。
- fixture 名は割り当てられた接頭辞のみ使う。
- 自分の担当外のファイル・fixture を書き換えない。

## 完了時
- 割り当てられたブランチに**コミット**する（`git switch -c <branch>` してから作業）。
- 最後に `cargo test --workspace` の結果と、追加したテスト名、既知の残件を報告する。

## 待ち合わせの絶対ルール（複数のエージェントがここで止まりました）
- **バックグラウンドの完了通知はあなたには届きません**（コーディネータにだけ届く）。
  「通知を待つ」状態で turn を終えると、起こされるまで永久に停止します。
  **turn を終えてよいのは最終報告が完成したときだけ。**
- 長いコマンドは前景で。timeout の上限は **600000 ms**（それ以上は指定しても 600 秒で切られる）。
  600 秒を超えるものは `nohup cmd > log 2>&1; echo EXIT=$? >> log` を 1 コマンドで投げてから、
  前景で `until grep -q EXIT= log; do sleep 30; done` を（切られたら同じものをもう一度）。
- **`pgrep` で他人の cargo test を待たない** — 他エージェントのテストが常に走っており、永久に抜けられません。
  自分のログファイルの番兵（`EXIT=` など）だけを見る。
- `cargo test --workspace` は最後の 1 回だけ。反復中は自分の `--test <name>` に絞る
  （全員が workspace を回すとマシンが飽和して全員が遅くなります）。
- slick 計測（`tests/slick_measure.sh`）を他のビルドと同時に走らせない。

## テストの分担（2026-08-31 改訂）
- **エージェントは `cargo test --workspace` を回さない。** 自分の `--test <name>` と、
  触った領域に直接関係する数本だけを前景で回す。ビルドは `cargo build --workspace`（エラー確認のみ）。
- 全体スイートの検証は**マージ時にコーディネータが 1 回**行う。これが正であり、
  エージェント側の全体実行はほぼ常に重複で、マシンを飽和させてきた（OOM/kill の原因）。
- 報告には「回したテストの範囲」を明記すること。全体を回していないことは欠陥ではない。

## 供給の継ぎ目（pickle_supply.rs / prelude の重複・優先順位）を触るとき
この領域は相互作用が最も濃く、2 スライス連続で「自分のテストは緑、隣が赤」の回帰を出しました。
`pickle_supply.rs`、`prelude*.rs` のシンボル供給・エイリアス・オーバーロード集合に触れたら、
報告前に**必ず**次を前景で回すこと:
`--test overloadshadow --test ambigmap --test setapply --test uniteq --test integral
 --test ordsummon --test mutcoll --test conform --test e2e`
（存在しないものはスキップ可。e2e は 460 本あるが最後の砦として省略不可。）

## 速度とマシン負荷（必読・2026-09-01 改訂）
- **テストは必ず `--release` で。** `cargo test` 既定の debug ビルドの `scala-rs` は
  実測で 1.6 倍以上遅く、e2e のように 1 テスト 1 コンパイルの suite では差がさらに開きます。
  正: `cargo test -p scala-rs-cli --release --test <name>`
- **並列上限は `.cargo/config.toml` が `RUST_TEST_THREADS=6` で掛けています。**外さないこと。
  各テストが `scala-rs` の子プロセス（時に `java` も）を撒くので、16 スレッドだと
  1 回の `cargo test` で 30 以上の重いプロセスが立ち、**ユーザーの他の作業が止まります**。
- **マクロ展開には 20 秒のタイムアウトがあります**（`SCALA_RS_MACRO_TIMEOUT_SECS` で変更、
  0 で無効）。マクロ実装はユーザーコードなので無限ループも停止もあり得ます。
  タイムアウトすると engine は kill され、その run の以降の展開は診断になります。
  **タイムアウトを無効化して原因調査する場合は、終わったら必ず戻すこと。**
- **中断したら迷子プロセスを回収**: `tests/reap_strays.sh`（引数なしで一覧、`--kill` で停止）。
  親が死ぬとコンパイル中の子が残ることがあります。

## 計測コストの実測値と、無駄を省くルール（2026-09-03 追加）
実測（16 コア、release、warm）:

| 工程 | 所要 |
|---|---|
| 増分ビルド（`check.rs` を触った場合） | **15 秒** |
| `cargo test --workspace --release`（108 バイナリ） | **7 分** |
| `tests/slick_measure.sh`（184 ファイル 1 周） | **4.5 分** |
| `tests/slick_subset.sh`（同じ 184 ファイルを最大 8 周） | **最悪 30 分超** |
| 実 scalac 1 回（JVM 起動込み） | **1.8 秒** |
| scala-rs 1 回（jar モード / 私有） | 0.4 秒 / 0.15 秒 |

**ここから来るルール:**
1. **`slick_subset.sh` は codegen（`crates/backend/`）を触ったときだけ回す。** 型検査だけのスライスでは
   数字は動かず、30 分を捨てるだけです。触っていないなら「codegen 未変更のため subset 省略」と報告に書けば十分。
2. **subset を回すときは `SLICK_SEED_LOG=<measure のログ> tests/slick_subset.sh`。**
   1 周目が `slick_measure.sh` と同一のコンパイルなので、その結果を種にして 4.5 分省けます。
3. **`slick_measure.sh` は着手時と完了時の 2 回だけ。** 途中経過を測りたくなったら、
   代わりに**自分の fixture** か、疑っているファイルだけを直接コンパイルしてください。
4. **dual-run の実 scalac は 1 回 1.8 秒。** fixture を増やすときは「1 ファイルに複数ケース」を優先し、
   ファイル数を増やさないこと（`conform` / `quasi` / `engine` が重いのはこれが理由）。
5. **`cargo test --workspace` は回さない**（従来どおり）。自分の `--test` と関連数本のみ。

## 計測ログは必ず自分専用のパスに（2026-09-03 追加、2026-09-06 に `CORPUS_LOG` を追記）

**共有の既定パスを持つのは `SLICK_LOG` だけではありません。** 少なくとも次は
すべて既定が共有パスで、指定しないと他のスライスやコーディネータのベースラインを
上書きします。実際に 2026-09-06 に `CORPUS_LOG` を既定のままコーパスを回した
スライスがあり、共有の `scalacorpus/corpus.tsv` が消えました（本人が申告した
ので取り直しで済みました）。

`SLICK_LOG` / `CATS_LOG` / `GITBUCKET_LOG` / `SCALALIB_LOG` / `CORPUS_LOG` /
`SLICK_SEED_LOG` / `BATTERY_OUT` / `SLICK_OUT` — 使うものは全部、自分専用の
ディレクトリを 1 つ作ってそこに向けてください。


`tests/slick_measure.sh` の `SLICK_LOG` は既定で
`…/scratchpad/slick/measure.txt` を指します。これは**コーディネータと全
エージェントの共有ファイル**で、あなたが計測するとベースラインが消えます。
必ず自分専用に固定してください:

```
SLICK_LOG=$MYDIR/measure.txt SLICK_RUN=$MYDIR/run ./tests/slick_measure.sh
```

同じ理由で、`SLICK_SEED_LOG` に共有パスを渡すときは**読むだけ**です
（`slick_subset.sh` は上書きしません）。

## 「単体で再現しない」ときの調べ方（2026-09-03 追加・実測から）

`agent/final2` が 3 スライス分の停滞を 1 回で抜けた方法です。
**ファイル集合の二分探索はしないでください**（1 パス 90 秒 × 8 回以上かかります）。
代わりに、**シンボルがどこから来たかを記録**してください:

```rust
// find_or_stub_java_class / adopt_binary_class などの入口で
eprintln!("{}: {}", name, std::backtrace::Backtrace::force_capture());
```

slick を 1 回通すだけで犯人の経路が直接出ます。この種のバグの正体は
**「あるシンボルが、ソースがその名前を書くより先に別の経路でシンボル表に
入り、先に入った答えが残る」**ことでした。

覚えておくと速い事実: **1 ファイルの中ではシグネチャ解決が本体の型付けより
先に全部走る**ので、同一ファイル内（さらには 2 ファイル）の「暖機」が
パラメータ型より先に来ることはありません。先に来られるのは
`parents_pass` 中に読まれる classfile だけです（＝型を名指しすること）。

## `pgrep` で待たないでください（2026-09-03 追加・実害が出ました）

`until ! pgrep -f 'cargo test --workspace'; do sleep 45; done` のような待ちは
**永久に終わりません**。理由は 2 つで、どちらも実際に起きました:

1. **`pgrep -f` は自分自身にマッチします。** そのループを走らせている zsh の
   コマンドラインには `cargo test --workspace` という文字列が入っているので、
   `pgrep` は必ず 1 件以上見つけます。**自分が終わるまで自分を待ちます。**
2. 他のエージェントとコーディネータが同じマシンで常に何かを回しています。
   他人のテストを待つ理由はありません。

**正しい待ち方**は、自分のログにセンチネルを書いて、それを待つことです:

```
nohup sh -c 'cargo test --workspace --release > $MYLOG 2>&1; echo "EXIT=$?" >> $MYLOG' >/dev/null 2>&1 &
until grep -q '^EXIT=' $MYLOG 2>/dev/null; do sleep 30; done
```

`$MYLOG` は**自分専用のパス**にしてください（他のエージェントと共有しない）。

## 診断の当て方（2026-09-03 追加・実測から）

* **「同一ファイル内のエラーは 1 つの根」は成り立ちません。** `ast/Type.scala`
  は 6 件で 3 根、`RewriteJoins.scala` は 4 件で 1 根でした。**必ず全件を
  個別に最小再現**してください。ブリーフが「カスケード」と書いていても、
  それは仮説です。
* **症状の出た場所と根は別ファイルにあることが多い**です。
  `value map is not a member of Any` の根は `map` ではなく、上流の
  `HashMap#filter` を classfile から読むときに **`Signature` 属性の無い
  mixin forwarder** を採ってしまい `(Any) => Any` になっていた件でした。
  型が `Any` / `Nothing` / 裸の型パラメータに潰れている症状は、**その式ではなく
  1 つ上流のメンバ供給を疑ってください**。
* **同じ症状が「両方の経路が届いていない」ことがあります。** `Ordering[Null]`
  は (a) コンパニオンが継承する low-priority trait の宣言を pickle から
  補っていない、(b) `$conforms` がスコープ構築の順序で永久に見つからない、の
  **2 つを両方直して**初めて通りました。1 つ直して数字が動かなくても、
  そこで「無関係だった」と結論しないでください。
* **拒否ルールを足して slick のエラーが増えたら、ルールが間違っています。**
  実 scalac が受理する形を拒否していないか、必ず最小再現で確認してください。
  逆に、nsc も拒否する形（`TC[_]` を普通の型位置に書く等）は**拒否が正解**で、
  免除するならパターン位置のような限定した条件だけにしてください。

## 長時間ジョブは切り離さない（2026-09-04 追加・11 時間を無駄にしました）

`nohup ... &` でシェルから切り離した `cargo test` が途中で死に、
**センチネル（`DONE` / `EXIT=`）が永久に来ない**まま待ちループが 11 時間
空回りしました。ログの最終更新は 02:13、気づいたのは 13:01 です。

- **切り離さないでください。** ハーネスが生死を追跡する形（Bash ツールの
  バックグラウンド実行）で起動すれば、死んだときに通知が来ます。
- どうしても待ちループを書くなら、**生存確認を必ず入れてください**:
  ログのサイズが N 分伸びていない、かつ対象プロセスが居ないなら中断する。
  センチネルだけを待つループは、ジョブが死んだ瞬間に無限ループになります。
- `pgrep` で待たないのは従来どおりです（他人のテストが常に走っています）。

## Merge main before your final verification (2026-09-04)

A slice that spent four hours on eleven real bug fixes had to be reverted
wholesale, because it branched from an older `main` and another slice had since
changed the same code (lambda lowering). Both were green on their own; together
they broke nine test binaries. Nothing was wrong with either piece of work.

So, **if you touch `crates/backend/src/gen.rs`, `crates/typer/src/check.rs`, or
anything else in the lambda / erasure / codegen path**:

1. Commit your work.
2. **`git merge main` into your branch** (it will have moved).
3. Resolve, rebuild, and **run your verification on the merged result** — not
   on your branch point.
4. Report the numbers from the merged tree.

A branch verified only against a stale base will be treated as unverified, and
the merge cost lands on the coordinator, who has less context on your change
than you do. If the merge turns out to be large, say so in your report rather
than guessing at a resolution.

## `classes=0` は成功に見える (2026-09-05)

`tests/*_measure.sh` が `errors=0` を出しても、**`classes` を見ないと騙されます**。
gitbucket の計測が一度 `errors=0 classes=0` を返しましたが、実体は
`SymbolTable::lub` の無限再帰による**スタックオーバーフローでコンパイラごと
落ちていた**もので、診断は 1 行も出ていませんでした。

**エラー数と生成クラス数は必ずセットで読んでください。** 型エラーが残って
いる間は `classes=0` が正常ですが、`errors=0 classes=0` は異常です。

同じ理由で、`files=` も確認してください。共有の slick チェックアウトが壊れて
いて `files=66` で測っていた例、別のエージェントが再 clone している最中に
当たった例が両方あります。**`files=184` でなければその計測は捨ててください。**

## What each check actually proves (2026-09-05)

Do not overstate what a harness verifies. Measured facts:

* **`tests/slick_subset.sh`** loads every class with
  `Class.forName(initialize = false)`. That parses the classfile and its
  constant pool, and **does not link**, so **method bodies are never verified**
  and an `invokedynamic` call site is never resolved. A broken bootstrap or a
  bad stack map passes it silently.
* **`javap -p` over every emitted file** parses the constant pool too. It is
  *not* weaker or stronger than the loader check — they overlap. It caught two
  files whose `CONSTANT_Utf8` length had silently wrapped past 65535.
* **`tests/slick_run.sh`** and **`tests/conform/`** are the only checks that
  execute code. A value-class bug once passed every other check in this list
  and only appeared at run time, because **the JVM verifier does not check
  interface types**.
* **`tests/scala_corpus.sh`'s `neg` pass rate is an upper bound.** A test counts
  as passing when scala-rs rejects the program *for any reason*, including the
  wrong one.

When you report, say which of these you ran. "Verified" without naming the
check is not a claim anyone can act on.

## When the coordinator re-verifies, and when it does not (2026-09-05)

For the coordinator, not for slices — written down because it is a recurring
cost and it should be a decision, not a habit.

**Skip re-verification entirely** when `main` has not moved since the slice ran
`git merge main`: `git diff --stat HEAD <branch>` after the merge is empty, so
the tree is byte-identical to the one the slice verified. That was true for
four merges this session.

**Re-verify only what the combination can reach** when `main` has moved. A
typer change merged onto a backend change cannot alter the classfile lint; a
size-only codegen change cannot alter `neg`.

**Re-verify in full** when the slice's own report cannot be trusted. Two
occasions this session earned this rule: one slice left an A/B revert
uncommitted in its working tree, so the green workspace run had measured a tree
*without* its fix; another reported a commit hash that does not exist and a
gitbucket figure that did not reproduce (1465 reported, 1588 measured). Both
were caught by re-measuring. Neither would have been caught by reading the
report more carefully.

## Do not measure the baseline. Read `tests/BASELINE.md` (2026-09-05)

`tests/BASELINE.md` carries the current numbers on `main` — every compile
measure, both execution harnesses, the full corpus, the test count and the
specialization ledger — taken from the verification run that gated the last
merge.

Measure **your** tree, compare against that file, report both. Do not spend
twenty minutes re-establishing "before" figures. In a six-slice wave that was
six identical measurements of the same commit.

If a number in that file disagrees with what an *unmodified* build of your tree
reports, **stop and report it**. Either the file is stale or your branch is not
where you think it is, and both make everything downstream meaningless.

The one case where you do measure a baseline yourself: your change reaches a
number the file does not carry (a subset of the corpus, a symptom count inside
a log, the size of a generated method). Then measure it on a throwaway branch
cut from `main` — never by reverting your own work in place, and never with
`git stash`.

## Run the checks your change can actually break (2026-09-05)

The battery has grown to six measures plus the workspace tests. Measured cost
on this machine:

| check | seconds |
| --- | --- |
| `cargo test --workspace --release` | **492** |
| `tests/slick_run.sh` | 75 |
| `tests/scala_corpus.sh` (default sample) | 50 |
| `tests/spec_classfiles.sh` | 27 |
| `tests/gitbucket_measure.sh` | 13 |
| `tests/scalalib_measure.sh` | 6 |
| `tests/slick_measure.sh` | 4 |
| `tests/cats_measure.sh` | 2 |

Running all of it twice — once on your branch, once after `git merge main` —
is over half an hour of waiting per slice. Do this instead:

**While iterating**: your own test, plus the seam list if you touched the
supply seams. Nothing else.

**Once, at the end, after `git merge main`**: the full battery. Not before the
merge as well — the pre-merge run tells you almost nothing the post-merge run
does not, and it is the post-merge numbers you report.

**Skip what your change cannot reach**, and say in your report which you
skipped and why:

* touched only `crates/parser/` or a diagnostic string ⇒ `slick_run.sh` and
  `slick_subset.sh` cannot change. The corpus and the four compile measures can.
* touched only `crates/backend/` ⇒ every compile measure is unchanged by
  construction (they stop before codegen while errors remain); run
  `slick_run.sh`, `slick_subset.sh`, and the corpus's `run` kind.
* touched name resolution, signatures, implicit search, or erasure ⇒ **run
  everything.** Those reach all six.

`cargo test --workspace --release` is never skippable. It is the only check
that covers the 150 test binaries, and at 8 minutes it is the floor.

## Time the battery every few slices (2026-09-05)

`tests/battery_cost.sh` times each check and prints a table. **Run it every few
slices, and whenever a check feels slower than it was.** Compare against the
table above; a line that has doubled is a bug report, not a fact of life.

This exists because `cats_measure.sh` spent weeks at 334 s to report 2929
errors, where the same 339 files took 4 s once `-Ykind-projector` was passed —
and the slow configuration was one that cannot be built at all, so nobody
should ever have measured it. Every slice paid for that because no one was

The 80x gap is itself a compiler bug (the error-recovery path for unresolved
`λ` / `*` names), recorded in `docs/cats.md`. **A check that got slower is
usually telling you something about the compiler, not about the check.**

## One wait loop at a time (2026-09-05)

A finished slice sent five separate "wait loop stopped" notifications after it
was already merged, because it had started a background wait for each long run
and none of them were cleaned up. Each is harmless on its own; together they
bury the report that matters.

**Start at most one background wait at a time, and let it finish before
starting another.** If you no longer need one, stop it rather than leaving it
to expire. When you report done, say so once.

## Check you are in your own worktree before you touch anything (2026-09-05)

First three commands of every slice, before any edit:

```
pwd && git log --oneline -1 && git status -sb
```

If `pwd` is the parent tree `/Users/shinji/projects/scala-rs`, **stop and report
without changing anything.** You are not supposed to be there. Some slices are
launched into an isolated worktree with the branch already cut, in which case

On 2026-09-05 five slices were launched without isolation and all landed in the

## Error counts and test counts are not the same estimate (2026-09-05)

When a brief hands you a cluster size, check which kind it is before you trust
it as a prediction of what your fix will be worth.

* **Error counts** (cats, gitbucket, the scala library) — `N` errors carry this
  symptom. Removing the root removes about `N` errors. On 2026-09-05 a brief
  said 179 for cats' `TypeClassType` cluster; the fix removed exactly 179.
* **Test counts** (the scala/scala corpus: `pos`, `neg`, `run`) — `N` *tests*
  stop at this diagnostic. A test only turns green when **every** wall in it is
  gone, so `N` is an upper bound on what your fix is worth, and it is often a
  very loose one. The same day, a brief said ≈200 `run` tests were blocked on
  the missing `scala.reflect.runtime` surface. Supplying it correctly moved
  **3**. The other 236 hit the next wall immediately — `mkToolBox`, `reify` of
  blocks, `TypeTag` materialisation — and now fail one layer deeper with an
  accurate diagnostic, which is real progress and is not three hundred tests.

Neither number is wrong; they answer different questions. What is wrong is
reading a test count as a yield. So:

* measure the subset your cluster actually names, before and after — the way
  that slice did (`CORPUS_KINDS=run CORPUS_SIZE=full CORPUS_FILTER='(…)'`)
* report the measured number, never the brief's
* a slice that moves 3 tests but replaces 236 misleading diagnostics with
  accurate ones has done real work. Say what it did; do not inflate it, and do
  not apologise for it either

## Three ways a slice ended badly on 2026-09-05 (all avoidable)

**0. `git stash` is shared across every worktree in this repo — do not use it.**
The stash is a single ref in the common git directory, so two slices stashing at
the same time push onto the same stack. On 2026-09-05 one slice's `stash pop`
applied *another slice's* stash into its tree and dropped its own. Both were
recovered from dangling commits, but only because someone noticed. For an A/B
baseline use a throwaway branch — `git switch -c ab-baseline`, revert, measure,
switch back — which is per-worktree and leaves a commit you can find again.

**1. Do not leave an A/B revert in the working tree.** One slice measured its
baseline by reverting its own fix in place, then ran out of budget before
restoring it. The workspace test that was running measured the reverted tree,
and the branch looked green for a change it did not contain. Measure A/B on a
committed throwaway branch (`git switch -c ab-baseline`, revert, measure,
switch back), never by editing the file you are about to be judged on.

**2. The workspace test does not fit in the foreground — plan for that.** It
takes about ten minutes and the Bash foreground cap is 600 s, so it *must* be
backgrounded; an earlier version of this section said to run it in the
foreground, which is not possible. What actually goes wrong is the waiting:
two slices ended while waiting on it and then started a *new* run on every
wake, at one point three concurrent runs in one worktree.

So: launch it **once**, as the last thing you do, writing to a log path of your
own (`> $MYDIR/workspace.log 2>&1; echo "EXIT=$?" >> $MYDIR/workspace.log`).
If your budget runs out before it finishes, **commit, and say in your report
that the workspace test is still running and where its log is.** That is a
complete, honest hand-off and costs the coordinator one command. Starting a
second run is not.

**3. A change that supplies new symbols must run `neg` in full, not a sample.**
`CORPUS_KINDS=neg CORPUS_SIZE=full`. A 250-test sample contained none of the
four tests that a new symbol turned from rejected to accepted.

## Put your e2e tests in your own file, not at the end of `e2e.rs`

Create `crates/cli/tests/<your prefix>.rs` and put your tests there. Cargo
picks up every file in `tests/` automatically, and the helpers are shared the
same way the existing per-slice files share them (`libctor.rs`, `tqmacro.rs`,
`ms_bigmethod.rs`, `engine.rs`).

The older instruction — append to the end of `e2e.rs` — was written to avoid
conflicts and now causes them. Every wave-7 slice that appended conflicted with
every other one that did, five times running, and each conflict had a slightly
different shape: sometimes the shared tail supplied one `}`, sometimes `);` and
a `}`, and once the earlier side was already closed and an inserted brace broke
the build. Not one of the slices that made its own file conflicted at all.

Add to `e2e.rs` only when your test genuinely belongs beside an existing one
there.

## Merging two branches that both append to `crates/cli/tests/e2e.rs`

Both sides end mid-function: the closing `}` of the last test belongs to the
*shared tail* after the conflict, not to either side. Keeping both sides
verbatim runs one function's body into the other block. Insert a `}` between
them. This failed to compile, which is the good outcome — but check it, do not
assume `git` got it right.

## "Pure code motion" is not automatically safe in Rust (2026-09-05)

Splitting a file can change behaviour with no error and no warning. A
`private fn foo` in the file being split **shadows** a `pub fn foo` arriving
through a glob import (`use some::module::*`); move its caller to a new file
and the local goes out of scope, so the glob one is selected silently. It
compiles, it type-checks, rustc says nothing.

This happened splitting `check.rs`: a private `is_assignment_op` had been
hiding `scala_rs_parser::ast::is_assignment_op`, which excludes operators
beginning with `=`, so `===` stopped being read as an assignment. gitbucket
went 1399 → 1402 and that number is the only thing that caught it.

So when you move code:

* **Verify with byte-identical output, not with counts.** `SLICK_OUT=<dir>
  tests/slick_measure.sh` on a throwaway branch cut from `main`, the same on
  your tree, then `diff -r`. All 1490 classfiles must be identical. A count
  that matches proves much less, and this defect changed a count by three.
* Sweep the crate for the shape before you start: a private item whose name
  also arrives through a glob import.
* Do not fix anything else in the same slice. If a number moves you need to
  know it was the move, and nothing else.

## Look at the library before believing a claim about the pickle (2026-09-06)

`docs/gitbucket.md` carried a diagnosis across several waves: 93–137 scalatra
errors were "a pickled *declaration* cannot be told from a definition", with a
measured warning that the naive fix made things worse (1693 → 2117) and a
prescribed order of work. A brief handed that to a slice as settled fact,
including the order.

It was wrong. One command settled it:

```
javap -p org.scalatra.ScalatraBase
  public default MultiMapHeadView params(HttpServletRequest);
  public default String           params(String, HttpServletRequest);
```

Two separately declared members. There was no collapsed pair to tell apart, and
neither `pflags::DEFERRED` nor the member-collapse path needed touching at all.
The real roots were elsewhere: overload references in value position ignored
implicit clauses (nsc's `isAsSpecific` sees through them), and a
declaration/definition pair failed to shadow when reached through a self type
or a nested class. gitbucket went 1399 → 1259.

So, before you accept any claim about what is or is not in a pickle:

* **`javap -p` the actual class.** It costs one command and it is the ground
  truth about what the library declares.
* A measurement attached to a diagnosis (1693 → 2117) can be a real
  measurement of a fix for a problem that does not exist. It tells you that
  *that* change was bad, not that the diagnosis was right.
* The brief may hand you an order of work. If the premise is false, say so and
  stop following it -- that is worth more than completing the assigned steps.

## The parent tree's binary goes stale, and it will fool you (2026-09-06)

`tests/*_measure.sh` and `cargo test` both rebuild. **A direct invocation of
`./target/release/scala-rs` does not.** The parent checkout's binary is
whatever the last build there left, which after a few merges is nothing in
particular.

On 2026-09-06 a slice reported that named-argument evaluation order was
broken, with a repro. The coordinator ran that repro against the parent tree's
binary, reproduced it, and wrote that a merged slice's verified claim was
wrong. Rebuilding gave scalac's answer. The fix had been working the whole
time; the binary predated it.

So: `cargo build -p scala-rs-cli --release` **immediately before** any manual
`scala-rs` invocation you intend to draw a conclusion from — and say in your
report that you did. This is the same rule as "measure your own worktree's
binary", which this brief has carried since 2026-08-30; the new part is that
the coordinator is not exempt, and that a stale binary produces a *plausible*
wrong answer rather than an obvious one.
